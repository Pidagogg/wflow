DEPLOYMENT — VPS / AWS / CLOUDFLARE / POSTGRESQL

AWS — EC2 DEPLOYMENT GUIDE

Run this self-hosted app on an AWS EC2 instance. The same container that runs locally runs on EC2; your data lives in ./data on the instance disk. Type your instance's IP into the EC2 address panel below to generate the exact commands for your machine.
1. Launch the instance.
  1. EC2 → Launch instance → AMI Ubuntu 24.04 LTS, type t3.small / t3.medium (2 GB RAM is plenty), storage 20 GB gp3.
  2. Create a key pair and keep the .pem — you need it to SSH in.
  3. Security group (inbound) — only open what you use:
    • 22 SSH — from your IP only.
    • 443 (+ 80) if Caddy/Nginx will terminate TLS.
    • 3001 only if you want a direct http://<ip>:3001 URL (skip it when you use the Cloudflare Tunnel panel below).
    • 3002 — never open. The admin panel is reached via an SSH tunnel (below) or ADMIN_ALLOWED_IPS.
  4. Do not attach an IAM instance role unless this app really needs AWS API access; if you do, enable IMDSv2 with hop limit 1 so only the instance itself can read its metadata.
2. First deploy.
  1. Connect:
    ssh -i your-key.pem ubuntu@<instance-public-ip>
  2. Install Docker (once):
    curl -fsSL https://get.docker.com | sh sudo usermod -aG docker ubuntu # log out and back in
  3. Clone the project, copy the env template and start it:
    git clone <your-repo-url> wflow && cd wflow cp .env.example .env nano .env # see the checklist below docker compose up -d --build
  4. Check it is up: curl -s http://<ip>:3001/api/nodes | head -c 120
3. Env checklist for a public AWS instance — add these to .env (the DEPLOYMENT settings form at the top of this tab writes the same file if the panel runs from the server):
PORT=3001 TRUST_PROXY=1 BF_COOKIE_SECURE=1 BF_ENCRYPTION_KEY=<64 hex chars> BF_ADMIN_USERNAME=myadmin BF_ADMIN_PASSWORD=<long random password> BF_ALLOW_REGISTER=0 BF_BLOCK_PRIVATE_URLS=1 # optional — hosted Postgres (e.g. RDS) instead of SQLite: # DATABASE_URL=postgres://wflow:<pw>@<rds-endpoint>:5432/wflow
Generate the encryption key on the server:
openssl rand -hex 32
4. HTTPS.
  1. Point your domain at the instance (Elastic IP / Route 53) and run Caddy for automatic TLS:
    docker run -d -p 80:80 -p 443:443 -v caddy-data:/data caddy caddy reverse-proxy --from flow.example.com --to localhost:3001
  2. …or use the Cloudflare Tunnel panel below (no open ports at all). Either way TRUST_PROXY=1 (already in the checklist) keeps rate limiting on real IPs; BF_COOKIE_SECURE=1 keeps login cookies HTTPS-only.
5. Data safety.
  1. ./data (workflows, agents, accounts, the SQLite DB and encrypted keys) lives on the instance's EBS root volume — snapshot it, or move the database to RDS.
  2. Back up BF_ENCRYPTION_KEY — losing it makes stored API keys unreadable.
  3. Change the default admin credentials and keep the panel off the public internet (step 1 above).

AFTER YOU DEPLOY — ADMIN PANEL & MAKING CHANGES

Can I still use the admin panel?
  1. Yes. The admin panel is a separate process on its own port (3002) that runs on the EC2 instance next to the app. You open it with an SSH tunnel from your PC (generated in the panel above):
    ssh -i your-key.pem -L 3002:localhost:3002 ubuntu@<instance-ip> # then open http://localhost:3002 in your browser
  2. Alternative: keep the port reachable only from your IP — add a security-group rule for 3002 from your IP and set ADMIN_ALLOWED_IPS to that IP in .env (everything else gets 403).
  3. Never expose port 3002 to the whole internet, and never keep the default admin credentials (Account tab / BF_ADMIN_USERNAME + BF_ADMIN_PASSWORD).
How do I change the site after it is deployed?
  1. Site text & settings — this admin panel: Page setup (name, tagline, banner), Cloud servers (where workflows are stored), Billing (Stripe), Database (users, SQL console), Deploy (domain, env, Postgres).
  2. Users' content — workflows and AI agents are edited in the app itself by the accounts that own them, any time, from any browser.
  3. Env / configuration — edit .env (or the forms on this tab) and restart:
    docker compose restart
  4. Code changes (new node types, UI changes, fixes) — edit the source in your repo, commit & push, then on the server:
    git pull && docker compose up -d --build
  5. Backups — snapshot the instance's EBS volume regularly; the whole ./data folder is on it.

SETUP GUIDE

1. Get a server (VPS).
  1. Any Linux VPS works (2 GB RAM is plenty). Install Docker:
    curl -fsSL https://get.docker.com | sh
  2. Clone the project, copy .env.example to .env, then start it:
    git clone <your-repo-url> wflow && cd wflow cp .env.example .env docker compose up -d --build
2. PostgreSQL (optional, recommended).
  1. Use the PostgreSQL service panel above (bundled compose service), or fill in a hosted connection string (Supabase / Neon) in the form at the top of this tab and press Test connection.
  2. Save to .env, then restart: docker compose restart. The schema is created automatically on first start.
  3. Accounts, sessions, the admin panel and the SQL Query node all run against PostgreSQL once DATABASE_URL is set.
3. Cloudflare.
  1. In Cloudflare DNS, point the domain at your server with proxy mode (orange cloud) on, or use the Cloudflare Tunnel panel above (no open ports needed).
  2. Option A — Tunnel (no open ports):
    cloudflared tunnel --url http://localhost:3001
  3. Option B — reverse proxy: forward 443 → 3001 with Caddy / Nginx, then enable Full (strict) SSL in Cloudflare.
  4. Enable TRUST_PROXY in the form above so rate limiting sees real client IPs, then restart.
4. Security checklist.
  1. Set BF_ENCRYPTION_KEY and back it up (encrypts sensitive DB values, incl. workflow node credentials).
  2. Change the default admin password (Account tab) and use strong login passwords.
  3. Keep ./data backed up — or rely on PostgreSQL backups instead.

OPTION A — BUNDLED POSTGRES SERVICE ?

docker-compose.yml ships a commented-out postgres service. Enabling it uncomments the service + depends_on and writes DATABASE_URL to .env, so the app switches from SQLite to PostgreSQL on the next docker compose up -d + restart. The schema is created automatically on first start.
Verify it worked:
docker compose ps docker compose logs -f postgres

OPTION B — HOSTED POSTGRES

Paste a connection string from Neon / Supabase / RDS / any Postgres 14+. Test it, then save it — the schema is created automatically.

PATRONI — HIGH-AVAILABILITY POSTGRES

Patroni turns PostgreSQL into a self-healing cluster with automatic failover — use it when one database is not enough. It needs 3+ nodes (etcd as the distributed config store) and a load balancer such as HAProxy in front. Enter the first node's host to generate a working starting configuration.
Point the app at the cluster. Connect through HAProxy (or the leader node) using the connection string from Option B above:
postgres://wflow:<password>@<haproxy-host>:5000/wflow?sslmode=require
Restoring a Patroni cluster is done with pg_restore / pg_basebackup on a node — the Backups tab keeps logical dumps you can feed to those tools.

KUBERNETES (K8s) DEPLOY

Run W flow on a Kubernetes cluster with a Deployment, Service, Ingress and a persistent volume for ./data. Ideal when you already have a cluster or want rolling updates without downtime.

DEPLOY TO THE CLUSTER

Build and push the image, then apply the generated manifests. Requires kubectl and docker on your machine.
Notes.
  1. The manifests mount a PersistentVolumeClaim at /app/data so the SQLite database, credentials and files survive pod restarts.
  2. For multi-replica production, point DATABASE_URL at managed Postgres (or Patroni — see the PostgreSQL tab) instead of SQLite and raise replicas.
  3. TLS is handled by the Ingress controller — install cert-manager and keep the cert-manager.io/cluster-issuer annotation shown in the generated manifest.
  4. Port 3002 (the admin panel) is intentionally not exposed by the Service — reach it with kubectl port-forward.

NGINX & TLS (HTTPS)

Terminate HTTPS with Nginx and a free Let's Encrypt certificate. Nginx forwards to the app on 127.0.0.1:3001; run the app with TRUST_PROXY=1 (Deploy tab) so rate limiting sees real client IPs.

SET UP NGINX + CERTBOT

Checklist.
  1. DNS: an A record for the domain must point at the VPS host above before running certbot, or the certificate request fails.
  2. Firewall: allow 80 and 443; keep 3001 closed to the public (Nginx proxies to it locally) and never expose 3002.
  3. Renewal: certbot installs a systemd timer automatically — check it with systemctl list-timers | grep certbot.
  4. After any change run nginx -t && systemctl reload nginx.
