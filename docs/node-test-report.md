## Bugs found

### 1. Router rules never matched a plain field name — FIXED (`server/executor.js`)

**Severity: high.** The Router read each rule's `field` with `renderTemplate(...)`, so a rule written as
`{ "field": "status", "operator": "equals", "value": "success" }` compared the literal string `status`
against `success` and never matched. Every item fell through to FALLBACK — which is exactly what the
node's own default rule tells the user to write. Only `{{status}}` worked.

Fix: resolve `field` with `getPath(item.json, field)` like the Filter and Sort nodes, while still accepting
`{{field}}` templates. Covered by `tests/nodes-logic.test.js`.

### 2. MySQL / MariaDB query nodes could never run a query — FIXED (`server/executor.js`)

**Severity: high.** `sqlMysql` / `sqlMariadb` parsed `params` into an OBJECT (`{}` by default) and passed it
straight to `mysql2`'s `execute()`. mysql2 throws `TypeError: Bind parameters must be array if
namedPlaceholders parameter is not enabled` for any object — including the empty `{}` — so **every** query
failed, masked until now because the failure was returned as a soft `error` field in a successful item.

Fix: enable `namedPlaceholders: true` on the connection (both `:name` objects and `?` arrays now work).
The PostgreSQL node gained positional-array support too: an array `params` is now passed through for
`$1, $2, …` instead of being ignored in favour of `:name` rewriting.

Verified against the installed mysql2 source (`lib/base/connection.js`, the bind-parameter check) and covered
by `tests/sql-integration.test.js` (run it with a real server — see below).

### 3. Twelve nodes reported success on failure — FIXED (`server/executor.js`)

**Severity: medium.** These handlers caught their own errors and pushed an `error` field into a SUCCESSFUL
output, so the run log showed success, a typo'd query did not halt the workflow, and the node's
"If this node fails" setting (stop / continue / retry) could never apply:

`clickupTask`, `compress`, `dataStore`, `emailSend`, `jsTransform`, `qrcode`, `sqlMariadb`, `sqlQuery`,
`sqlQuestdb`, `sqlSqlserver`, `todoistTask`, `whatsappSend`

They now throw tagged errors, so the executor's `onError` handling applies as documented:

| Node(s) | Code raised |
| --- | --- |
| `jsTransform` | BF-7001 code error |
| `whatsappSend`, `todoistTask`, `clickupTask` | BF-4001 / BF-4003 / BF-4002 by HTTP status |
| `emailSend` | BF-4002 service error |
| `sqlQuery`, `sqlPostgres`, `sqlMysql`, `sqlMariadb`, `sqlQuestdb`, `sqlSqlserver` | **BF-6010 (new)** database query failed |
| `compress` (no upstream files) | BF-6005 no file content |
| `qrcode`, `dataStore` | BF-1001 unexpected error |

New error code added to `shared/errors.js` and `ERRORS.md`: **BF-6010 — Database query failed**.

One test expectation was corrected as a consequence: `compress` was removed from the EXPECT_PASS list in
`tests/all-nodes.test.js`, because with no upstream files it now correctly fails with BF-6005 instead of
reporting a fake success. Covered by `tests/nodes-actions.test.js` and `tests/nodes-files.test.js`.

### 4. Execute Workflow Trigger emitted an empty object on a plain run — FIXED

**Severity: low.** Every other trigger emits a representative sample payload when the workflow is run from
the editor; `executeWorkflowTrigger` returned `{}`. It now falls back to `samplePayloadFor(node, ctx)` — a
real sub-workflow call is still seeded directly by the engine and never reaches the handler.

### 5. 67 more nodes reported success on failure — FIXED (`server/executor.js`)

**Severity: high.** Item 3 turned out to be the visible part of a much wider pattern: 67 hand-written
service nodes still caught their own HTTP failures and emitted them as a SUCCESSFUL item. Three shapes:

- an `error` field beside `sent: false` / `uploaded: false` / `posted: false` — `slackSend`, `resendEmail`,
  `twilioSms`, `s3Upload`, `webdavUpload`, `twitterPost`, …
- `created: false` with NO error at all — `githubIssue`, `notionPage`
- a normal-looking payload for a lookup that found nothing — `weather`, `cryptoPrice`, `wikipediaSearch`,
  `redditSearch`, …

Consequence: a wrong API token, a rate-limited endpoint or a 500 from GitHub looked like a successful step,
the run did not stop, and the node's "If this node fails" setting (stop / continue / retry) could never
apply. All 67 now throw the same classified errors the 215 descriptor-driven service nodes already used —
BF-4001 auth failed · BF-4002 service error · BF-4003 rate limited · BF-4xxx request failed — via a shared
`serviceFailure()` helper, so status handling is identical across the codebase.

Application-level failures that arrive with HTTP 200 are classified too: `{ok: false}` from Slack/Telegram,
`{status: 0}` from Pushover, `{success: false}` from Pipedrive, `{cod: "404"}` from OpenWeather and
`{status: "fail"}` from the IP-geo lookup all now fail with BF-4002.

Deliberate exemption: the **HTTP Request node keeps returning `status` / `ok` / `data`** for any response — its
purpose is to hand the caller the raw reply and let an IF node branch on it.

Covered by `tests/nodes-http-errors.test.js`, which discovers the node list from the executor source: 76
network nodes (plus the exempt `http`) × {500, 4xx, network failure, 200-with-error} — every one must fail.
The offline stub in
`tests/helpers/fake-services.js` returned canned 200s, which is exactly why this went unnoticed; it now returns
realistic payloads per service so the success paths are still genuinely exercised.

### 6. Seven legacy executor aliases have no catalog entry (informational)

`extractText`, `extractTable`, `extractStructured`, `extractPdf`, `extractArchive`, `fileMetadata` and
`webhookOut` are handled by the executor but cannot be added from the palette. They are kept deliberately so
workflows saved before the merge keep running.

## Not fully testable offline

These nodes are exercised for config validation and the failure path; their SUCCESS path needs a real
server/socket: `docker`, `emailSend`, `executeCommand`, `ftp`, `git`, `kafka`, `mqtt`, `redis`, `sqlCratedb`, `sqlMariadb`, `sqlMysql`, `sqlPostgres`, `sqlQuestdb`, `sqlSqlserver`, `sqlTimescaledb`, `ssh`.

The SQL ones have ready integration tests — they are skipped (not silently passed) until a server is given:

```bash
export TEST_POSTGRES_URL=postgres://user:pass@localhost:5432/testdb
export TEST_MYSQL_URL=mysql://user:pass@localhost:3306/testdb
node --test tests/sql-integration.test.js
```

Everything else — including all 215 external HTTP service nodes — runs against a mocked network: the
executor builds the real request and parses the real response shape, and success / 401 / 403 / 429 / 5xx /
timeout / malformed-body paths are asserted.

## Observations & inconsistencies

- **No registration gaps:** every catalog node is dispatchable (171 explicit executor cases, 215
  service-descriptor nodes, 23 extra core/logic nodes; every trigger also handled by kind).
- **Empty input:** every node returns a classified result for zero upstream items — none crash.
- **Manual output:** all 473 nodes skip their handler and pass the typed JSON through exactly.
- **Unicode:** all nodes survive non-ASCII text, emoji, quotes, backslashes and tabs.
- **MySQL placeholder docs:** the shared SQL field help says "$1 / ? placeholders"; for MySQL the
  recommended forms are now `?` with an array or `:name` with an object.
